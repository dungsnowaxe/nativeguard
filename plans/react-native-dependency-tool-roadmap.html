Product plan · Expo / React Native dependencies

Build a compatibility intelligence engine, not just another dependency updater.

The product should feel like a smarter, friendlier fork of Expo Doctor and rnx-kit align-deps: same core category, but with stronger dependency graph analysis, patch-level exceptions, Renovate/Dependabot PR review, and a curated workaround knowledge base.

CLI-first AI-native optional GitHub Action Patch/workaround registry Expo + bare RN

Final recommendation

Yes, this is worth building, but the wedge should be very specific: stable-state protection and intentional exception handling for Expo/RN dependencies.

Do not position it as a general Renovate replacement. Do not position it as a magical AI updater. The pain is sharper: “Expo recommends version A, but version A has a bug. Can I safely use B, and what exact patch, override, workaround, or config change do I need?”

Product thesis: Expo Doctor and rnx-kit tell you whether your dependency set matches a known policy. This tool should tell you whether your dependency set is stable, why it is not, and what safe remediation path preserves stability.

Updated product shape

  • Not a wrapper: it should implement its own analyzers inspired by Expo Doctor + rnx-kit.
  • Not only install --fix: it should support intentional off-matrix versions.
  • Not only semver: it should reason about Expo SDK, RN minor/patch, native modules, New Architecture, package manager behavior, and known breakages.
  • Not only local CLI: it should also review Renovate/Dependabot PRs through a GitHub Action or GitHub App.

Core workflows

  1. Doctor mode: analyze current repo stability.
  2. Explain mode: explain one dependency/version against Expo SDK + RN + package manager context.
  3. Plan mode: produce a safe upgrade/remediation plan.
  4. Apply mode: apply only deterministic fixes: manifest edits, overrides, excludes, package extensions, patch files.
  5. PR review mode: comment on Renovate/Dependabot PRs when they break the stable state.

nativeguard explain react-native-reanimated@4.1.0
nativeguard plan --target expo@54
nativeguard review-pr --base main --head renovate/react-native-svg-15.x
nativeguard apply --safe

Stable-state model

The important abstraction is not “latest version”. It is stable state: a dependency graph that is known, intentional, reproducible, and supported by evidence.

  • Green: matches Expo/RN matrix and no known issue.
  • Blue: intentional off-matrix version with evidence and config exclusion.
  • Yellow: works with required override/workaround/patch.
  • Red: likely unsafe due to native API, peer, New Architecture, or known regression.
Renovate/Dependabot PR review becomes simple: compare the PR’s new graph against the repo’s previous stable state, then report any newly introduced risk.

How can a CLI get GitHub Issues workarounds or patches?

The CLI should not randomly scrape GitHub Issues at install time and blindly apply code. That would be slow, unreliable, and dangerous. Instead, use a hybrid knowledge model.

1. Local static rules
Bundle a small, versioned rule pack with high-confidence compatibility data: Expo SDK matrix, RN versions, known peer dependency ranges, package manager recipes, and curated “known issue” records. This can be JSON or SQLite, shipped with the npm package.
2. Remote registry
Offer an optional online registry for fresher rules. The CLI can fetch it with caching, ETag, and lockfile-style pinning. CI can pin nativeguard-rules@2026.07.08 for reproducibility.
3. Evidence index
Store links and extracted metadata from GitHub Issues, PRs, releases, changelogs, Expo discussions, React Native Directory, and docs. Do not store full copyrighted content; store summaries, issue IDs, versions, affected ranges, fix versions, confidence, and source URLs.
4. On-demand research
For unknown cases, the CLI can run an optional research command or MCP/AI workflow that searches GitHub and docs, then outputs a proposed rule. The proposal must be human-reviewed or CI-approved before becoming trusted.
5. Verification gate
Even if a workaround exists, the CLI should verify locally: reinstall, run static checks, run Expo/RN validation, run TypeScript, optionally run iOS/Android build, and check whether the patch applies cleanly.

What to build first

  • Own doctor implementation: not a wrapper, but compatible mental model.
  • Expo SDK matrix loader: know expected package versions.
  • RN profile model: support Expo and bare RN projects.
  • Package manager adapters: npm, pnpm, Yarn, Bun detection and safe remediation primitives.
  • Stable-state snapshot: store current dependency graph status in CI artifact or repo file.
  • PR review: detect whether a Renovate/Dependabot PR introduces instability.

What not to build first

  • No dashboard-first product. Too far from the repo-level pain.
  • No broad dependency SaaS. Renovate, Dependabot, Socket, Snyk, Mend, etc. already own broad update/security workflows.
  • No auto-generated patches without verification. Trust will die fast if it breaks builds.
  • No huge local scraped database. Start curated and small.
  • No “AI-only skill”. Skill should guide agents to call deterministic tooling.

Risks and mitigations

Risk Mitigation
Bad patch breaks production No blind apply. Require confidence levels, local verification, and human approval for source patches.
Knowledge base becomes stale Rules have expiry dates, evidence dates, SDK scopes, and CI warnings when a rule is old.
Too much maintenance Start with top painful libraries and community-submitted rules. Do not attempt full npm coverage.
Expo changes official tooling Position as exception/remediation layer, not Expo Doctor clone only.
Renovate already owns PRs Complement Renovate. Review dependency PRs instead of opening all updates yourself.

Go / no-go decision

Go if…

  • You can build a useful doctor report in under 4–6 weeks.
  • Real projects show repeated false positives, off-matrix dependency needs, or patch-package usage.
  • PR review catches issues normal Renovate/Dependabot cannot explain.
  • Users say: “I wish I had this during my last Expo/RN upgrade.”

Do not go all in if…

  • The first version is only a nicer wrapper around existing tools.
  • The rule registry cannot stay accurate.
  • Most fixes require manual expertise and cannot be encoded as reusable recipes.
  • Teams are unwilling to run another CI check.
Practical verdict: build the CLI + PR review MVP first. Treat the workaround database as the moat, but start tiny and curated. AI comes after the deterministic engine is useful.
