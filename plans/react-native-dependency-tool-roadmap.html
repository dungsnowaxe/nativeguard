Project purpose

NativeGuard exists to help Expo and React Native teams make dependency decisions with evidence instead of guesswork. The product should answer whether a dependency graph is known stable, intentionally off-matrix, temporarily patched, or unsafe to ship.

The open-source CLI should become the shared compatibility layer between local developers, CI, Renovate/Dependabot, and AI coding agents. Its job is not to replace official tools; its job is to preserve the reasoning that happens after official tools say “this version is unexpected” or “this package is unknown”.

OSS mission: make React Native dependency risk visible, explainable, reviewable, and reproducible before a team discovers the problem in Xcode, Gradle, EAS Build, or production crash reports.

Open-source positioning

  • Primary users: RN app maintainers, Expo teams, platform engineers, library maintainers, and CI owners.
  • Primary moment: before merging a dependency PR, upgrading Expo SDK/RN, enabling New Architecture, or deleting a patch.
  • Core asset: a curated, evidence-backed compatibility rule registry.
  • Trust model: deterministic analysis first, human-reviewed rules second, AI-assisted research only as a proposal path.
  • Anti-goal: do not become a general npm updater, security scanner, or dashboard-first SaaS.

High-value user pain points

The best open-source wedge is not broad dependency freshness. It is the set of moments where a React Native app looks healthy at the JavaScript package level, but the native runtime, build system, Expo SDK matrix, or team workflow is about to fail.

App maintainer pains

  • “Expo recommends A, but B fixes my bug.” Teams need to know whether an off-matrix version is a safe exception or a future crash.
  • Warnings without decision support. A warning from Expo Doctor or React Native Directory still leaves the maintainer deciding whether to downgrade, exclude, replace, patch, or ignore.
  • Native failure after clean install. The dependency tree can install while CocoaPods, Gradle, codegen, Hermes, Fabric, or EAS Build fails later.
  • Patch amnesia. A patch-package file may be essential, obsolete, or harmful after a version bump, but the repo rarely records why it exists.
  • Upgrade blockers are discovered too late. Teams often learn that one native module blocks Expo SDK/RN migration only after hours of build failures.

Platform / CI owner pains

  • Dependency PRs lack RN context. Renovate and Dependabot can open the PR, but they do not know whether the new graph is stable for this Expo SDK, RN version, architecture mode, or package manager.
  • CI checks become noisy. Teams either block on too many warnings or turn checks off because the output does not distinguish known exceptions from new risk.
  • Monorepo resolution is invisible. Workspaces, hoisting, duplicate React/RN installs, and package manager-specific overrides can change runtime behavior without obvious package.json changes.
  • Policy is hard to encode. A team may allow off-matrix versions only with evidence, expiry, and owner approval, but existing tools do not model that workflow.
  • Cross-repo learning is lost. A workaround found in one app does not automatically protect another app in the same organization.

Library maintainer pains

  • Users report “does not work on Expo SDK X” without enough environment data.
  • Compatibility status differs across iOS, Android, web, New Architecture, and Expo Go/dev builds.
  • Release notes rarely become machine-readable compatibility ranges.

New Architecture pains

  • Directory metadata may be missing, stale, or too coarse for a specific package version.
  • Fabric support, TurboModule support, bridgeless behavior, and codegen issues are often conflated.
  • A package can be compatible in bare RN but still awkward in Expo prebuild or EAS Build.

Agent workflow pains

  • AI agents can edit dependency files confidently while lacking Expo/RN compatibility facts.
  • Agents need structured facts, allowed actions, and verification gates instead of unbounded web guesses.
  • Generated fixes must be explainable enough for humans to review in PRs.

Core workflows

  1. Doctor mode: analyze current repo stability.
  2. Explain mode: explain one dependency/version against Expo SDK + RN + package manager context.
  3. Plan mode: produce a safe upgrade/remediation plan.
  4. Apply mode: apply only deterministic fixes: manifest edits, overrides, excludes, package extensions, patch files.
  5. PR review mode: comment on Renovate/Dependabot PRs when they break the stable state.

nativeguard apply --safe

Stable-state model

The important abstraction is not “latest version”. It is stable state: a dependency graph that is known, intentional, reproducible, and supported by evidence.

  • Green: matches Expo/RN matrix and no known issue.
  • Blue: intentional off-matrix version with evidence and config exclusion.
  • Yellow: works with required override/workaround/patch.
  • Red: likely unsafe due to native API, peer, New Architecture, or known regression.
Renovate/Dependabot PR review becomes simple: compare the PR’s new graph against the repo’s previous stable state, then report any newly introduced risk.

Adoption paths

The CLI should become useful in small steps. A maintainer should be able to adopt read-only reports first, then CI checks, then PR review, then safe remediation and private rules.

Local developer

  • Run nativeguard doctor before upgrading Expo SDK or React Native.
  • Run nativeguard explain package@version before accepting an off-matrix dependency.
  • Generate a redacted environment snapshot for bug reports and library maintainers.

CI gate

  • Fail only on new red risks by default.
  • Warn on stale exceptions, unknown packages, and low-confidence rules.
  • Upload stable-state snapshots as artifacts for later PR comparison.

Renovate / Dependabot

  • Review the dependency graph diff instead of only the package that changed.
  • Comment with risk, evidence, required actions, and verification commands.
  • Suggest packageRules, labels, or approval requirements for risky native packages.

Library maintainer

  • Ask users to attach nativeguard doctor --report to compatibility issues.
  • Publish machine-readable support ranges or rule snippets with releases.
  • Use fixtures to confirm Expo/RN/New Architecture support claims.

AI coding agent

  • Call NativeGuard for facts before editing dependency files.
  • Use JSON output to choose allowed actions and required verification.
  • Open rule proposals when no trusted rule exists.

Team product later

  • Track private exceptions across repositories.
  • Show patch expiry and upgrade blockers before release planning.
  • Let platform teams approve rules and policies centrally.

How can a CLI get GitHub Issues workarounds or patches?

The CLI should not randomly scrape GitHub Issues at install time and blindly apply code. That would be slow, unreliable, and dangerous. Instead, use a hybrid knowledge model.

1. Local static rules
Bundle a small, versioned rule pack with high-confidence compatibility data: Expo SDK matrix, RN versions, known peer dependency ranges, package manager recipes, and curated “known issue” records. This can be JSON or SQLite, shipped with the npm package.
2. Remote registry
Offer an optional online registry for fresher rules. The CLI can fetch it with caching, ETag, and lockfile-style pinning. CI can pin nativeguard-rules@2026.07.08 for reproducibility.
3. Evidence index
Store links and extracted metadata from GitHub Issues, PRs, releases, changelogs, Expo discussions, React Native Directory, and docs. Do not store full copyrighted content; store summaries, issue IDs, versions, affected ranges, fix versions, confidence, and source URLs.
4. On-demand research
For unknown cases, the CLI can run an optional research command or MCP/AI workflow that searches GitHub and docs, then outputs a proposed rule. The proposal must be human-reviewed or CI-approved before becoming trusted.
5. Verification gate
Even if a workaround exists, the CLI should verify locally: reinstall, run static checks, run Expo/RN validation, run TypeScript, optionally run iOS/Android build, and check whether the patch applies cleanly.

Rule registry design

The registry is the moat, but only if it stays precise. Rules should be small, scoped, evidence-backed records that explain a compatibility decision in a specific project context.

Rule lifecycle

  1. Proposed: created from a maintainer, user report, release note, issue, or AI-assisted research.
  2. Reproduced: tied to a fixture, minimal reproduction, or enough environment evidence.
  3. Trusted: reviewed by maintainers and safe to use in default rule packs.
  4. Stale: past review date, superseded by a package release, or lacking current Expo/RN coverage.
  5. Retired: no longer relevant and kept only for historical explanation.

Rule fields that matter

  • Scope: package, version range, transitive/direct status, Expo SDK, RN version, platform, architecture mode, package manager.
  • Symptom: install warning, pod failure, Gradle failure, codegen error, runtime crash, rendering regression, or CI-only failure.
  • Action: pin, bump, downgrade, exclude, override, resolution, package extension, config change, patch, replacement, or manual verification.
  • Evidence: issue, PR, release note, changelog, reproduction repo, fixture result, or maintainer confirmation.
  • Governance: confidence, owner, review date, expiry date, and human approval requirement.

Conflict handling

  • If two rules disagree, prefer the rule with narrower context and stronger evidence.
  • If confidence is low, report uncertainty instead of giving a hard recommendation.
  • If the rule only covers one platform, never imply cross-platform safety.
  • If a package has no metadata, classify why: JS-only, native unknown, private/internal, abandoned, or missing directory entry.

Registry verification

  • Schema validation for every rule.
  • Snapshot tests for report output.
  • Fixture projects for common Expo/RN/package-manager combinations.
  • Optional clean-machine build checks for high-impact rules.
  • Scheduled stale-rule reports so maintainers review old workaround advice.

Open-source readiness checklist

Before public launch, NativeGuard needs more than a useful CLI. It needs a contribution system that lets the community add compatibility knowledge without turning the project into an unreviewed pile of package anecdotes.

Repository shape

  • @nativeguard/core: project scanner, dependency graph model, context detector, rule evaluator, and report schema.
  • @nativeguard/cli: terminal commands, JSON output, CI-friendly exit codes, and local config loading.
  • @nativeguard/rules: public compatibility rules, fixtures, schema validation, and evidence metadata.
  • @nativeguard/action: GitHub Action wrapper for PR comments, check annotations, and stable-state diffing.
  • fixtures/: real-world Expo/RN project shapes across npm, pnpm, Yarn, monorepos, New Architecture, and bare RN.

Contributor workflow

  • Every rule PR must include affected package, version range, Expo SDK/RN context, platform, architecture mode, symptom, action, confidence, and evidence link.
  • Every rule must pass schema validation and at least one fixture test or documented reproduction reason.
  • Rules should include reviewAfter or expiresAfter so stale workarounds are visible.
  • Maintainers should label rules as confirmed, community-reported, workaround, deprecated, or needs-repro.
  • Generated or AI-assisted rules must be submitted as proposals, never merged as trusted facts without human review.

Trust and safety rules

  • No blind source patch application by default.
  • No scraping GitHub Issues during normal installs or CI runs.
  • No rule should recommend an action without confidence, evidence, affected range, and rollback guidance.
  • Risky actions require explicit flags, clean git state checks, and a generated diff preview.
  • CI mode should distinguish new risk, known exception, stale exception, and unknown.

Public launch minimum

  • Readable README with the exact problem statement and five realistic examples.
  • Stable JSON report schema for agent, CI, and dashboard use.
  • Exit code contract for local and CI workflows.
  • Rule schema docs plus contribution templates.
  • Security policy, code of conduct, license, changelog, and maintainer escalation path.
  • Comparison page explaining how NativeGuard complements Expo Doctor, React Native Directory, rnx-kit, Renovate, Dependabot, Snyk, and Socket.

Testing and release discipline

NativeGuard will only earn trust if every recommendation can be traced, tested, and released predictably. The test suite should protect both code behavior and compatibility knowledge.

Fixture matrix

  • Expo managed: clean app, unknown package, off-matrix dependency, and Expo SDK upgrade case.
  • Expo prebuild: generated native folders, config plugin changes, Podfile/Gradle drift, and EAS profile variance.
  • Bare React Native: RN minor alignment, New Architecture flags, native module duplicate, and peer dependency mismatch.
  • Monorepo: workspace app, local package, hoisted dependency, duplicated React/RN, and private package classification.
  • Package managers: npm lockfile, pnpm lockfile and overrides, Yarn resolutions/packageExtensions, Bun read-only detection.

Verification layers

  • Unit tests for scanners, rule matching, semver/range handling, and policy decisions.
  • Golden snapshot tests for terminal output and JSON reports.
  • Fixture integration tests that run the CLI against realistic repo trees.
  • Rule registry CI that validates schema, evidence shape, stale dates, and conflicting scopes.
  • Optional expensive checks for selected fixtures: TypeScript, Expo Doctor parity checks, pod install, Gradle sync/build, or EAS dry-run equivalent where feasible.

Security and privacy

  • Redaction rules for environment reports: tokens, registry URLs, private scopes, internal paths, and CI variables.
  • No default network access in normal analysis unless the user opts into remote rule updates.
  • Remote rules must be versioned, cacheable, and pin-able; CI should be reproducible offline after cache warmup.
  • Patch and apply commands must require clean git state, preview diffs, and explicit confirmation.
  • Security policy must cover malicious rules, unsafe remediation, dependency confusion, and accidental private data disclosure.

Release process

  • Separate release channels for CLI/core and rules.
  • Changelog entries distinguish engine changes, rule additions, rule removals, stale-rule changes, and breaking report schema changes.
  • Rule pack releases include generated summaries of new affected packages and retired workarounds.
  • Public v1 requires docs, examples, fixtures, contribution templates, CI, and at least one real-project validation report.
  • Breaking changes require migration notes for config, JSON schema, rule schema, and CI exit codes.

Build order before public v1

  • Own doctor implementation: not a wrapper, but compatible mental model with explainable findings.
  • Schema-first foundation: define config, rule, report, snapshot, and exit-code contracts before broad feature work.
  • Expo/RN context model: support Expo managed, Expo prebuild, bare RN, New Architecture, and generated native folders.
  • Package manager adapters: npm, pnpm, Yarn, and Bun read-only detection with package-manager-specific advice.
  • Stable-state snapshot: store current dependency graph status in CI artifact or repo file.
  • PR review: detect whether a Renovate/Dependabot PR introduces instability across direct and transitive dependencies.
  • Contributor-ready rules: ship rule validation, examples, fixtures, and review workflow before asking the community to contribute.

What not to publicize early

  • No dashboard-first product. Too far from the repo-level pain.
  • No broad dependency SaaS. Renovate, Dependabot, Socket, Snyk, Mend, etc. already own broad update/security workflows.
  • No auto-generated patches without verification. Trust will die fast if it breaks builds.
  • No huge local scraped database. Start curated and small.
  • No “AI-only skill”. Skill should guide agents to call deterministic tooling.
  • No public release with vague warnings. If the tool cannot explain a risk, it should report uncertainty instead of pretending to know.

  • Users say: “I wish I had this during my last Expo/RN upgrade.”

Do not go all in if…

  • The first version is only a nicer wrapper around existing tools.
  • The rule registry cannot stay accurate.
  • Most fixes require manual expertise and cannot be encoded as reusable recipes.
  • Teams are unwilling to run another CI check.
Practical verdict: build toward an OSS-ready v1, not a thin public MVP. Treat the workaround database as the moat, but require schemas, fixtures, docs, governance, and CI integration before launch. AI comes after the deterministic engine is useful and trusted.
